# Lab5 CI 实验方案

## 目标与位置

延续本人 Lab2 Flask 聊天应用，通过 GitHub Actions 自动检查代码。

- 课程仓库：`/Users/carrie/isse-labs`，远端 `CarrieJiang-X/isse-labs`。
- 实验仓库：`/Users/carrie/isse-lab5-chat-ci`，远端 `CarrieJiang-X/isse-lab5-chat-ci`，分支 `main`。
- 最终课程分支及目录：`lab5/2400018814-蒋翌楠`。
- 原始应用：课程仓库 `lab2/蒋翌楠-2400018814`。

## 最小设计

直接复制 Lab2 的 app.py、frontend、运行依赖和示例配置。保留现有网页、JSON 持久化及 CRUD 接口。使用空初始数据，原 Lab2 文件和个人聊天记录保持原状。

后端只增加 `LAB5_DATA_DIR` 数据目录配置，在读取历史记录前生效。正常运行继续使用默认 data 目录；测试和冒烟脚本使用临时目录。

使用 pytest fixture 隔离数据，用 mock 替换 requests.post 返回固定模型回复，只设置占位 Key。核心测试是一条记录的创建、查询、修改、删除，以及空消息返回 400 且不新增记录。根据真实覆盖率报告补充必要测试，统计完整 app 模块的行覆盖率，门槛为 70%。

只保留一份 .github/workflows/ci.yml。先由 push 到 main、向 main 的 PR 触发 ubuntu-latest 上的 Python 3.12 测试；准备 Python、安装运行和测试依赖、执行覆盖率命令。

功能回归实验：暂时让 DELETE 返回成功但不删除记录，保留原测试预期；在 GitHub 保存一次失败日志，然后恢复删除行为并推送修复，保留两次运行链接。

直接使用课程 templates/smoke_test.py 骨架，适配 app:app、首页 /、连通性接口 /api/hello 与预期 JSON。先本地验证进程启动、HTTP 响应与退出清理，再将该命令加入同一 CI。

最后将同一工作流的 runs-on 改为 self-hosted，在本机 macOS ARM64 runner 工作区创建虚拟环境、安装依赖，执行同样的覆盖率和冒烟检查。runner 安装在仓库外，前台启动，实验后停止。

## 执行与验证

1. 同步课程 main 并创建课程分支；导入 Lab2 应用至实验仓库。
   验证：两份仓库远端、分支和绝对路径正确，初始应用可导入。
2. 添加测试与云端 CI。
   验证：本地和云端测试通过，app 行覆盖率至少 70%。暂停讲解 mock、断言、覆盖率与工作流。
3. 制造功能失败并修复。
   验证：不同提交对应的两次真实 Actions 运行分别失败和通过，能解释断言差异。暂停观察日志。
4. 适配冒烟检查并切换本机 runner。
   验证：云端和本机均完成测试、覆盖率与 HTTP 冒烟检查；网页与终端能对应同一次本机运行。暂停讲解执行位置。
5. 整理课程提交。
   验证：最终 app、四类真实截图、导出的真实对话齐全，runner 已停止，课程 PR 只包含本人 Lab5 目录。最后用思考题检查理解。

## 材料约束

不复制真实 .env、API Key、个人聊天数据、.git、虚拟环境或 runner 程序。截图及轨迹省略注册 token。对话轨迹由真实导出或可访问的分享链接提供，不用摘要代替。日常操作由 Agent 完成，用户在关键节点阅读说明和观察实际结果。

## 方案取舍

选择直接复用 Lab2，因为代码最少、与课程要求直接对应。复用 Lab4 会额外带入监控逻辑；重写聊天应用会增加与 CI 无关的改动，因此均不采用。
